# 独立 DDR 校准与读写诊断

本工程 `projects/08_ddr_diag` 专门诊断 Ti60F225 主板上的 U12 MT41K128M16JT-125:K（D9PTK）。使用与 C7 一致的 DDR 引脚、1.5 V SSTL、400 MHz DDR CK、100 MHz AXI/core 和 tFAW=50 ns；保留必需的 DDR VREF 引脚。原 C7、CPU 固件和其构建报告不改动。

**该镜像会破坏整片 256 MiB DDR 的内容。** 工程没有 CPU、Flash 访问、相机、HDMI或传感器任务，适合在正常程序停止后单独临时加载。电脑端已经执行 RTL 仿真及 FPGA 实现检查，但尚未在实物运行；实际下载、DDR 校准/读写、断电恢复都须保存板上证据。

## 文件与复现

2026-10-31 实际完成 Interface/map/P&R/配置生成。9 组 setup 和 9 组 hold 时钟关系均非负，最差裕量分别为 +0.324 ns、+0.027 ns；XLR 6,875/60,800（11.31%），Memory Blocks 22/256，无 DSP。配置流计 581,713 字节（含容器信息的保守计数），镜像身份以 BUILD_RECORD.json 为准。厂家 DDR FIFO 的冗余/未驱动辅助复位信号警告，以及未消费的 PLL feedback 顶层输入警告仍保留，未修改受保护源码；这不替代板上 PHY 验证。

- 一键构建：根目录 `28_build_ddr_diag.cmd`。
- FPGA JTAG 临时加载文件：`fpga_bitstreams/ddr_diag_100mhz/ddr_diag.bit`。
- `.hex` 是 FPGA 配置流，供归档审阅；本流程使用 `.bit` 和 JTAG 模式，不执行 Flash 擦写。
- `fpga_bitstreams/ddr_diag_100mhz/BUILD_RECORD.json`：本次镜像 SHA256、时序、引脚和验收范围。
- `logs/ddr_diag_tests.json`：12 项 AXI 场景、4 条实际 UART 位级解码记录及 8 项日志解析检查的结果，使用缩小的行为内存模型，不模拟厂家受保护 DDR PHY。
- `logs/ddr_diag_build.json`、`logs/ddr_diag_check.json`：Interface/map/P&R/配置生成结果与输入身份。

接收机器需要现有 C 项目、已固定版本的 C7 DDR 私有头文件/控制器、Efinity 2026.1.132、Icarus 与 Python 3，重新运行构建以生成本机路径。安装目录与大型 mapped netlist 不作为交接内容。

## 上板操作

1. 断电后移除摄像头、传感器和蜂鸣器等外接模块。按已经核对的供电/跳线保持 DDR 及 MIPI bank 电压，不改 J2/J3。
2. 接厂家配套电源与正确的 USB/JTAG 下载接口。确认 Efinity Programmer 能识别下载器及 Ti60F225；不把蓝牙 COM 口当作板卡 UART。
3. 打开对应 UART，设置 **115200、8N1、无流控**，记录原始文本；不要主动切换 DTR/RTS。记录主板、下载器、COM 口和 `.bit` 的 SHA256。
4. 在 Efinity Programmer 选取本轮 `ddr_diag.bit`，选择 **JTAG** 模式进行 FPGA SRAM 临时配置。本工程没有执行下载操作；不要把 CPU HEX 或旧 TinyML `.bit` 当作此镜像。
5. 如果已错过最初日志，可按板上 **KEY0/SW0（FPGA C4）** 重新开始。不要使用 CRESET_N 替代它：CRESET_N 会清除/重载 FPGA 配置，可能返回旧 Flash 程序。
6. 等待校准与全容量测试完成。当前逐个 128-bit 单 beat 操作，以简单、可定位为目的，不作带宽测试；运行可能需要数十秒至数分钟，不能因测试中没有立即 PASS 就判定失败。串口约每秒继续报一次状态。

若临时 JTAG 配置导致 UART 设备重新枚举，重新选择板卡对应端口，再按 KEY0 开始单次记录。没有专用下载器信息前不提供猜测的 FTDI 通道、USB index 或 COM 编号。

## LED 状态

仅使用两颗已经核对的板载 LED：

| 指示 | 管脚 | 行为 |
|---|---|---|
| LED0 心跳 | P13，3.3 V，高有效 | 由独立 25 MHz 晶振驱动，每秒亮半秒；即使 DDR/core PLL 未锁定仍可观察 |
| LED1 测试状态 | N13，3.3 V，高有效 | 校准等待/测试中为每秒短闪；全部通过后常亮；失败或超时后快速闪烁 |

心跳不出现时先检查是否加载了正确镜像、供电、KEY0 和参考晶振；LED1 的短闪不能区分等待与读写阶段，须读取 UART 状态码。不要用主板 CDONE 灯推断 DDR 校准结果。

## UART 格式和判断

每条记录示例格式：

```text
DDR|S=03 L=3 C=1 I=12 E=00 A=00000000 N=00001234 P=00012340
```

示例仅用于解释字段，不是实测日志。全部字段用十六进制：

| 字段 | 含义 |
|---|---|
| S | 00=刚复位；01=等 PLL；02=等 DDR 校准；03=测试中；06=完成；E0=AXI/数据错误；F0=PLL 等待超时；F1=校准等待超时 |
| L | 两个 PLL 的锁定状态，正常为 3 |
| C | 厂家控制器 cal_done，正常为 1 |
| I | 厂家初始化状态，辅助定位卡住阶段，不作单独通过判据 |
| E | 00=无错误；01=测试中校准丢失；02=AXI 无进展超时；03=写响应/ID 异常；04=读响应/ID/RLAST 异常；05=数据不匹配 |
| A | 首次失败的 AXI 字节地址；无错误时为 0 |
| N | 已逐项核对的数据 word 数；全部通过必须为 **04000019**（67,108,889） |
| P | 当前 AXI 字节地址，运行时仅作为进度参考 |

监控时钟独立于 DDR/core，PLL 超时阈值约为复位后 2 秒，校准等待阈值约为复位后 10 秒；这两个值是诊断超时设置，不是厂家规定的校准时长。每个 AXI 事务无握手进展超过约 100 ms 记错。AXI 失败后停止测试并复位 DDR 控制器，保留错误信息；按 KEY0 才会重新测试。

运行中的多位状态/地址为跨域观测值，可能出现短暂不一致；终态数据锁存稳定。因此验收需要连续收到两条完整的 `S=06 L=3 C=1 E=00 N=04000019` 记录，不能只凭一行或一颗灯判定通过。

测试先写入/读回 0 地址及 24 个地址位探测点，检查从 bit4 到 bit27 的地址别名；再对 [0,0x10000000) 逐 16 字节访问，完成全零、全一、地址相关、混合地址相关四轮“全写后全读”。每个 128-bit word 均核对，失败立即停止。混合图案是确定性数据图案，不宣称真随机或 DDR 带宽压力覆盖。

## 保存和验证日志

一次日志只对应一次加载/KEY0/冷启动尝试，不混入多次失败与重试。保存为文本后，在工程根目录运行：

```powershell
python -X utf8 tools/check_ddr_uart.py "日志路径\ddr_attempt_01.log" --output "logs\ddr_attempt_01_check.json"
```

校验器要求至少两条完整容量 PASS、最后一条仍为 PASS，并拒绝超时/错误、错误计数、未知状态与截断记录。`PASS_LOG` 只说明保存内容符合协议，不能独立证明板卡身份、镜像来源或冷启动；必须同时保存本轮 `.bit` SHA256 和实物记录。

先完成临时 JTAG 配置与 KEY0 复位测试，再重复断电上电并重新 JTAG 加载，记录每次校准与读写结果。临时配置断电失效；这种操作证明的是“冷上电后重新配置可通过”，不等同于从 Flash 自动冷启动。Flash 启动及 CPU/AI/视频并发验收仍须另外进行。
